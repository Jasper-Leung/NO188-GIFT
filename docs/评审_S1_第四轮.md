## 3. 问题清单

### P0 — 挡在"能给人看"前面的

#### P0-1　路面在每一帧里都读成蓝紫色霉斑，而它是全屏最大的一块表面

**现象**：`04_ride`、`04b_villain`、`12b_day`、`12c_dusk` 四张的近处路面都是
**深灰底上盖着一层蓝黑色的斑块**，近处读成霉，近处那条白色边线更是
**全画面里最脏的东西**——它自己在抖。正午那张稍好，但路面仍然深到接近纯黑。

**这不是观感偏好，是三个可以定位到行的成因叠在一起**（`assets/shaders/asphalt.gdshader`）：

1. **反照率低了一个数量级**（`:9-10`）
   ```glsl
   uniform vec4 asphalt_color    = vec4(0.168, 0.170, 0.178, 1.0);
   uniform vec4 grain_dark_color = vec4(0.068, 0.068, 0.074, 1.0);
   ```
   这两个值带 `source_color`，Godot 按 **sRGB** 解释。`0.168 sRGB → 线性 0.023`，
   `0.068 sRGB → 线性 0.005`。真实沥青的反照率大致是线性 0.10~0.15（≈ sRGB 0.35~0.42）。
   也就是说底色比真实沥青**暗 4~5 倍**，而 `grain`（`:69-74`）还要往更暗的那档混 0.6。
   顺带那两个常量本身就是**偏蓝的中性灰**（b > g > r），线性空间里这个偏置会被放大。

2. **法线扰动的梯度大到逐像素走样**（`:147-152`）
   ```glsl
   vec2 dp = wp * 11.0;                       // 11 周/米 ≈ 9cm 一个特征
   vec3 micro = vec3((d0 - dxn) * 16.0, 1.0, (d0 - dzn) * 16.0);
   NORMAL = normalize(mix(NORMAL, normalize(micro), 0.45));
   ```
   `(d0 - dxn) * 16.0` 里那个 **16.0** 加上 **0.45** 的混合强度，
   让每一个 9cm 的微面片都在陡峭地翻转。玩家眼高 1.6m、看 1~3m 处的路面时，
   一个像素盖住好几个特征——于是**每个像素要么翻到天上（接到蓝天 → 蓝）、
   要么翻到地里（黑）**。这就是那片蓝紫胡椒的来源，它不是"斑块"，是走样。

3. **湿斑把粗糙度和金属度一起拉低**（`:98-99, :139, :144`）
   ```glsl
   float wet = smoothstep(0.42, 0.56, fbm2(wp * 0.13 + vec2(7.0, 2.0)));
   col   *= 1.0 - 0.18 * wet;
   rough -= 0.20 * wet;
   METALLIC = wet * 0.12;
   ```
   在一个**本来就接近纯黑**的表面上再降 0.2 粗糙度 + 给 0.12 金属度，
   等于把湿斑变成一面朝天的镜子。它映的是天空。

**为什么上一轮没看见**：上一轮 P0-1 是「草皮齐腰成墙」。
草盖着路的时候，路面是全图最小的表面；把 `DENSITY` 从 5.0 降到 2.2 之后，
路成了全屏最大的一块，而它是坏的。**这一层是修好上一层才露出来的。**

**为什么 30 条回归一条都没报**：`--headless` 用 dummy renderer，**不编译着色器**。
而 `verify_asphalt_shader.gd` 守的全是**读源码文本**的那一族
（uniform 有没有被读、边线宽度、`plaza_mode`、默认值 == `RoadBuilder` 的常量表）——
它守的是"边线画没画出来"，守不到"路面是什么颜色、法线有多陡"。
这和 `edge_line_color` 是同一个族的另一半：那条是**声明了没读**，
这条是**读了但量错了量**。

**建议改法**（三处都是常量级改动，不动结构）

- `asphalt_color` → 约 `vec4(0.36, 0.355, 0.345, 1.0)`（sRGB 口径，暖中性）
- `grain_dark_color` → 约 `vec4(0.22, 0.215, 0.210, 1.0)`，并把混合系数从 0.6 降到 0.45
- `micro` 的两个 `16.0` → `4.0`，混合强度 `0.45` → `0.22`；同时把 `dp` 的频率
  从 `11.0` 降到 `6.0`（特征从 9cm 变 17cm，跨过像素边界的概率直接降一半）
- `METALLIC = wet * 0.12` → `wet * 0.03`（沥青没有金属度可言，那是为了假高光）

改完的验收方式只有一个：`lookdev_journey` 的 `04_ride` + `lookdev_water`（水面会映路面）。

#### P0-2　五件签名物件里，有三件画成了通用色块

这个游戏的全部身份就是"云 / 茶 / 琴 / 竹 / 禽"。
我在**集齐面板**（`14_ending_终局二选一`，1280×720 原生）上逐个看过这五个图标：

| 物件 | 我看到的是 | 代码里是 |
| :--- | :--- | :--- |
| 云 | 一朵云 ✓ | `FragmentIcon._draw_cloud`，四团鼓包 |
| **茶** | **一个空心椭圆**，看不出是壶是杯是蛋 | `_draw_teacup`：上下两个**半径 10 的半圆弧，圆心差 6px** |
| **琴** | **一个圆丘 / 一座山** | `_draw_guqin`：五点透镜 + 底边 + 四条横线 |
| 竹 | 三根带节的竹子 ✓ | `_draw_bamboo` |
| 禽 | 一只鸟，有喙有尾有栖枝，翅是留白的 ✓ | 走 `FragmentIcon.paint_bird` |

**茶的算法问题**（`scripts/FragmentIcon.gd:60-66`）：
两个 `draw_arc` 的圆心分别是 `(0, 2)` 和 `(0, -4)`，半径都是 10——
上下半圆**错开 6px** 拼出来的不是杯子，是一个透镜形。
把手是半径 4px 的 1.5px 宽小弧（占图标宽度 5%，看不见）；
水面是半径 3px 的 1.0px 宽浅色弧（占图标面积 1.5%，看不见）。
第三轮 P1-2 记的"壶是纯黑剪影、注水时看不到水位"——**几何修了，观感没修，
因为它从一开始就不是一个壶的形状，加大水位也救不回来**。

**琴的算法问题**（`FragmentIcon.gd:69-80`）：
五点 `(−18,3) (−10,−5) (0,−7) (10,−5) (18,3)` 加一条底边 = 一个**对称的透镜**。
古琴的辨识特征是**不对称**：琴额那端是方的、宽的，琴尾那端收细，
底下有两只雁足。这三样一个都没有。

**同样的病在五个小游戏里有两处**：

- **云**（`minigame_云`）：要描的那条轨迹是一个**几乎处处外凸的土包**，
  底边平、顶上是圆弧、底下中间挤着四个很小的圆。
  第三轮 6g 节把它从八边形改成"9/40 个尖角 + 平底"，判据是
  **"尖角占顶点的比例"**——它量的是"不是多边形"，量不到"是云"。
  一朵云的关键是**相邻鼓包之间的凹口**，现在一个都没有。
- **琴**（`minigame_琴`）：琴身其实是**画对了的**——左端方、右端收细、
  有岳山 / 琴轸 / 雁足 / 13 个徽（这些第三轮都修过，代码里能看到注释）。
  但四条弦是按 `_draw_string_h` 的 `board` 全宽画的（`:284`），
  而琴身是内收的多边形，于是**弦两头都戳在木头外面**，
  四个金色小方块悬在半空。那四块是键位提示（`:256`），
  正好落在弦的末端上，看起来像琴上镶了四个金属钉。

**为什么回归全绿**：`verify_mini_game.gd` 6g 节的判据全是**几何量**
（尖角比例、平底、徽的个数与分布、砍倒那截的伸出量），
而"这看起来像不像一朵云 / 一把琴"**没有一个数能量**——
和第三轮自己写下的那条教训完全同构：
> **判"是不是云"和判"是不是多边形"是两个量，而这一族只写了后者。**

**建议改法**

- **茶**：直接画**盖碗**（茶烟小筑本来就该是盖碗）。四笔：碗身弧 + 一道横向的口沿
  + 口沿上一个盖钮 + 底下一个圈足。盖碗的剪影在任何尺寸下都不会读错，
  而"壶"要靠壶嘴和壶把两个小构件撑着，那两个在小尺寸上必然消失。
- **琴（图标）**：把五点透镜改成**不对称**——左端方而高、右端收细，
  底下加两只雁足。这一改完它立刻不会读成山了。
- **云（轨迹）**：在相邻鼓包之间**留出真正的凹口**（现在是
  `minf` 逐列取最小值，鼓包半径之和大于圆心距，凹口被填平了），
  并把底下那四个小圆去掉——它们是"底边平"的实现细节，代价是四个噪点。
- **琴（小游戏）**：弦按**琴身在该 y 处的实际半宽**裁，不要按 `board` 全宽。
- **补一条量"像不像"的判据**：禽已经有了一条（翅是留白，只有像素量得到）。
  茶/琴/云要各补一条同类判据——比如**剪影在 22px 盘里的可辨识性**：
  缩小到 `FragmentBar` 那个尺寸之后，取墨掩膜算它与"椭圆/圆丘/凸包"
  三个基形的 IoU，低于门槛就红。**这一条是纯几何、无头可跑、不碰画笔。**

### P1 — 会被评委当场指出来的

#### P1-1　黄昏时草皮过曝成饱和橙，路面纯黑——明度关系反了

`12c_dusk` 原生图：近处草皮是一片**高饱和的橙**（约 sRGB 200,120,40），
而沥青是**接近纯黑**。低角度夕阳下，**竖着的草皮卡片**正对太阳、
**横着的路面**只吃到掠射光，明度差被拉到这个程度是物理上说得通的，
但**路面之所以扛不住，是因为 P0-1 已经把它的反照率压到线性 0.023**。
太阳一压到 9°（`DayCycle.DUSK_SUN_ANGLE_MAX = 24.0` 插值出来的），
路面就没有任何余量可剩。

**这是 P0-1 的下游，不是独立的一条**：修完反照率之后，
黄昏的明度关系大概率自己就正了。所以**先修 P0-1，再回来看这张图**，
不要单独去调 `DUSK_SUN_ENERGY`（现在是 0.70，第三轮为了治"草不受光"从 1.05 降下来的）。

同一张图上还有一个第三轮 P2-5 降级过的老问题，现在看**比当时记录的严重**：
天空上半是**一片纯红**（约 sRGB 190,0,0，绿蓝两路基本为零），
下半是**一片淡粉**，两者交界是一条**2~3px 的硬边**，没有任何过渡。
`DUSK_SKY_TOP = (0.10, 0.12, 0.28)` 是深蓝紫，`DUSK_SKY_HORIZON = (0.95, 0.52, 0.26)`
是暖橙——**常量是对的，图上却不是这两个色**。
这一条我没能定位到成因（`verify_day_cycle` 全绿、`fog_sky_affect` 有断言守着），
如实记为**未定位**，不猜。

推力在 21m 处压过 `Player3D.ACCEL = 8.0`），并且写着**回归验证：无**。
本轮补一条：**这一族现在有一把尺子了**（`play_newcomer.gd` 的骑乘日志），
可以把它钉成断言——"骑向站点的最后 20m，平均速度 ≥ 8m/s"。
现在实测远低于 8（30s 走了 9m，平均 0.3m/s）。

**要注意别修错方向**：`STATION_OFFSET = 18.0` 而 `STATION_PASS_RADIUS = 15.0`，
所以**玩家在 3m 外就够得着打卡圈**，并不需要真的骑到 18m。
问题不是"墙挡住了打卡"，是**"墙之外那一片没有视觉引导"**。
正解是在 `SOFT_BOUND` 边缘画一道**看得见的软边界**（草色变浅 / 一道土径），
而不是削弱推力——削弱推力会让人真的骑进 25m 的硬墙里。

#### P1-3　背面编辑器那两个按钮读不出来

`16_postcard_back_背面写字`：「确认 / Confirm」和「跳过，直接导出」
是**深灰字压在深灰底上**，没有边框、没有底板、没有焦点框。
第一次看这张图时我**没找到按钮**，是找到之后才确认它在那儿。
粗测对比度约 **2.5:1**，低于 AA 的 4.5:1。

同一个文件的其余部分做得很对（预览 452px、字号 60、提示语齐全），
所以这是**一处没跟上**而不是整体没做。第三轮 §8.6 的教训
（「可读性是个乘积，量任何一个因子都量不到它」）在这里的对应物是
**"按钮是个三维量：底板 + 边框 + 字，三样都要在"**。

#### P1-4　结算页的五个色块比地图还抢眼，而且不带任何信息

`15_postcard_明信片`：中段五个色块（云淡蓝 / 茶黄绿 / 琴褐 / 竹绿 / 禽橙）
是整张卡上**最响的东西**，而它们不带任何信息——玩家已经知道是哪五件了。
带信息的抬头（路线图 + 「已过 16 驿」+ 右半那列五行到访次数）反而更安静。
另外 `No.188` 在底部 300px 内**出现了两次**（一次在框里、一次在句子里）。

第三轮 P2-3（右列与蜡封挤在一起）**已修**：右半那列现在干干净净，
蜡封在右上角，两者不打架了。这一条是新提的。

### P2 — 打磨项

**P2-1　顶栏中段有 390px 的空档。** `05_prompt_打卡提示` 顶栏从
`x≈400`（心神结束）到 `x≈790`（下一处开始）是空的。
这是第三轮那根 `SIZE_EXPAND_FILL` 弹簧的**设计后果**：
右端钉死在按钮排左边 16px 是对的（"不许留死区"那条回归守的就是它），
但"钉死右端"和"中段不许空"是两件事。**这条断言本身是对的**，
只是它的解把长度变化全推给了中段那一根弹簧。
可选改法：下一处那一组靠右、心神那一组靠左，中间空着就空着，
但把**衬底的高度或 alpha**在中段降一档，让空档读成"留白"而不是"黑带断了"。

**P2-2　`verify_grass_scatter` 本轮三条红**（详见 §5）——
铺满 3799ms（门槛 2.5s）、最慢帧 43.56ms（门槛 20ms）、7/1200 帧超 40ms。
**如实说明：我不能断言这是产品回归。** `CLAUDE.md` 自己记着
「同一份代码最慢帧在 19/23/20/34/49/55ms 之间乱跳」，
43.56 落在那条噪声带里；而我这台机器本轮同时在跑带窗口的 Godot。
**需要在干净机器上单跑一遍再定性。**

**P2-3　`MiniGameZither` 的雁足画在木头上面，读成琴身上一个缺口**（第三轮 P2-4 的残留）。
`foot_polys()`（`MiniGameZither.gd:185-193`）把两只脚挂在
`tail_h * 0.55`，而琴身在该处的半高约 `0.9 * tail_h`——
**0.55 仍在木头里面**，于是两只脚叠在琴腹上形成一个深色 V 形缺口。
注释写着"两只都挂在**琴腹以下**"，但那个常数没做到。
`11_synthesis` 那张的琴尾（原生放大）能直接看到这个 V。
改成 `tail_h * 1.05` 就出去了。第三轮判它"已修"是因为岳山那条确实修好了。

**P2-4　五个图标仍然是三份手抄。** `FragmentIcon` / `Postcard` / `FragmentBar`
三个文件各有 `_draw_cloud` / `_draw_teacup` / `_draw_guqin` / `_draw_bamboo`
四套实现（15 个画法里只有禽走了 `FragmentIcon.paint_bird` 一个出处）。
三处的注释都写着"和 XXX 同一套鼓包、同一段轮廓算法"——**但它们是抄的**。
第三轮已经把这个家族的一条教训写进 `CLAUDE.md`
（「同一个形状在 N 处出现时，先确认那 N 处是 N 份抄写还是 N 种实现」），
并且只对禽做了收口。**剩下四件是同一个问题的四份未修。**

**P2-5　旅途币是常驻 HUD 元素，而玩家可能一辈子不花它**（见 §2.3 的 719 枚）。
要么让顶栏那一栏在玩家一次都没进过驿铺时不出现，要么在第一次路过驿铺时
由 `World3D` 主动提示一次。前者更诚实。

**P2-6　禽的配色仍然偏低对比。** 第三轮 §8.6 记的
「麻雀 2.2:1、燕子 1.7:1 本体对卡底仍低于 3.0:1」——
本轮看 `minigame_禽` 仍然是靠描边兜住的，颜色没动。
（顺带确认这一屏的**形状**确实修好了：白鹭 / 燕子 / 麻雀 / 乌鹊四个剪影两两不同，
这一条第三轮做对了。）

## 7. 给下一轮评委的三句话

1. **这一轮的 P0 全部是"上一轮修好之后才露出来的"。**
   草皮的墙拆了，路成了全屏最大的一块，而路是坏的。
   这说明这个项目的整改有一个稳定的模式：**每修好一层，下一层才进入视野**——
   所以"这一轮全绿"从来不是"没有下一层"的理由。

2. **1819 条无头断言一条都没报，而三条 P0/P1 我全是在原生分辨率的
   截图上放大看出来的。** 这个项目的回归工程是同类里我见过最扎实的，
   但它守的**几乎全是"接线"和"几何"，几乎不守"观感"**——
   而这轮三条里没有一条是接线问题。
   可推广的一条：**当一个项目把"我不测观感"写进自己的文档时，
   要把它读成"观感由看图负责"，而不是"观感不用管"。**

3. **未定位的一条我留白，不猜**：黄昏天上一片纯红 + 一条 2~3px 硬边，
   而 `DUSK_SKY_TOP` / `DUSK_SKY_HORIZON` 两个常量读出来都不是那个色。
   `verify_day_cycle` 全绿、`fog_sky_affect` 有断言守着。
   **我倾向于"天空之外还有一层东西在画那块红"，但我没有证据，所以不写进结论。**
