## 判据纪律（先读这一节，它比下面任何一批都重要）

这一轮最贵的两个发现不是某个 bug，是**同一个错误第三次出现**：

> **判据钉在「我写下的那个数」上，而不是钉在「玩家眼睛看到的那张图」上。**

三个现成的例子，同一族：

| 判据 | 量的东西 | 玩家看到的东西 |
| :--- | :--- | :--- |
| `verify_day_cycle` 新增 3 条 | `min/max(DUSK_SUN_COL) >= 0.50` | 黄昏草皮饱和度 **0.796** |
| `lookdev_journey` `dusk_gr >= 0.10` | 门槛松 3.8 倍（实测 0.378） | 一条 **63px 高**、b/r=0.23 的红带 |
| `verify_mini_game` 6g 节 | 「不是多边形」（尖角比例） | 「像不像一朵云」 |

**本计划的硬规矩**：每一条新增判据必须满足下面三条，否则不写。

1. **量渲染结果**（像素 / 纯函数返回的剪影），不量常量。
2. **带一条正对照**，证明这把尺子量得出要它量的那个差别。
   没有正对照的阈值，绿了也说明不了任何事。
3. **阈值取自实测基线**，并且在写进代码前先确认它**真的会红**。

> 这不是新规矩。`CLAUDE.md` 的陷阱清单里已经写着
> 「判『是不是云』和判『是不是多边形』是两个量，而那一族只写了后者」。
> **第四轮 §7 又写了一遍。这一轮是第三次，所以它被提到计划的最前面。**

## 第一批：路面色相（半天，收益最大）

**为什么排第一**：路面是全场唯一大面积、近水平、朝天的表面，
在任何一张骑行截图里都占 40%~60%。它是「第一眼」。

**已确认的事实**（第五轮实测，五个区域）

| 区域 | 中位 sRGB | `b−r` | 中位饱和度 |
| :--- | :--- | :-: | :-: |
| 正午 中段 `12b_day` | (98,95,126) | **+28** | 0.246 |
| 反派戏近景 `04b_villain` | (120,120,157) | **+37** | 0.236 |
| 骑行近处 `04_ride` | (86,86,104) | +18 | 0.173 |
| 黄昏 中段 `12c_dusk` | (27,23,33) | +6 | 0.303 |

**已排除的三个成因**（各做过一次对照实验，见评审 §2）

- ❌ `EMISSION = vec3(0.06,0.07,0.08) * rim`（`asphalt.gdshader:170`）——
  归零后 `b−r` +28→+29，纹丝不动
- ❌ `ambient_light_sky_contribution` / `ambient_light_color`——
  归到 0.62 并转暖后**逐像素不变**；探针确认值被读到，
  说明这个旋钮在 `ambient_light_source = 3` 下对漫反射无效
- ❌ 掠射角菲涅尔反射——`SPECULAR = 0` 压暗了 13 个单位，蓝只掉 3 个

### 步骤

- [ ] **1.1 先做那唯一一步确认实验**（5 分钟）
  把 `asphalt.gdshader` 的 `ALBEDO = col;` 临时改成 `ALBEDO = vec3(0.35);`，
  重跑 `lookdev_journey`，量同一片区域。
  - 仍然是蓝的 → **成因确认在漫反射**，材质无关
  - 变中性了 → 成因在 `col` 那条链上，回去查 `dirt_color` / `shoulder`
- [ ] **1.2 按 1.1 的结果选旋钮**（二选一）
  - **A（推荐）**：给路面材质补一份暖的半球环境项，
    在 `fragment()` 里自算一份以 `NORMAL` 为轴的暖色补光加进 `ALBEDO`。
    绕开那个失效的环境光旋钮，不动天空外观。
  - **B**：收 `DayCycle.DAY_SKY_TOP` 的蓝
    （`(0.27,0.53,0.95)` 的 b 是 r 的 **3.5 倍**，天空蓝得对美术不友好）。
    注意 B 会同时改变天空观感，要重拍 `12b_day` 的天带。
- [ ] **1.3 调完重拍 `lookdev_journey`，跑下面两条判据**

### 验收判据（加进 `lookdev_journey.gd`，取样区域就是上面那张表）

- [ ] 「正午路面中位 `|b−r| ≤ 12`」（现在 +28）
- [ ] 「正午路面中位饱和度 `≤ 0.12`」（现在 0.246）
- [ ] **正对照**：「同一帧草地的 `|b−r| ≥ 25`」
  —— 草地现在实测 `b−r = −73`（明显偏绿）。
  **没有这条，把路面调成纯灰也照样绿。**
- [ ] **黄灯**：阈值写到 12 之后先确认它在当前代码上**真的会红**，
  再去改着色器

## 第二批：天穹地平线那条 2 像素硬缝（半天）

**为什么排第二**：它横贯整幅画面的上方，而且在正午和黄昏都出现——
**一天里玩家见到它的时间加起来比路面还多**。

**已确认的事实**（第五轮逐行扫描）

```
正午  y=130 (118,151,218)  →  y=140 (209,215,224)   绿 +91 蓝 +64
黄昏  y=132 (177, 78, 48)  →  y=134 (187,154,162)   绿 +76 蓝 +114
```

成因是 `ProceduralSkyMaterial` 的**天穹地平线**：sky 半球与 ground 半球
在视线水平方向上是两半，而 `sky_curve = 0.15` 让天空那侧在接近地平线时
**还没收敛到 `sky_horizon_color`**，于是缝的上侧是饱和的天顶色、
下侧是接近地平线的淡霾。

**判据现状**：`SKY_ROWS = [0.10,0.14,0.18,0.22]` 四条**全部落在缝的上侧**，
缝以下整个区域一条断言都没有。

### 步骤

- [ ] **2.1 先补判据（让它红）**
  - 「天带内相邻两行的最大通道跳变 `≤ 24`」
  - **正对照**：「地形轮廓那一行的跳变 `≥ 40`」
    ——证明这个量在真轮廓上读得到、在平天空上读不到
- [ ] **2.2 取样带下移跨过缝**：`SKY_ROWS` 加 `0.21 / 0.24`
- [ ] **2.3 收紧已经太松的门槛**：`dusk_gr >= 0.10` → `>= 0.45`
  （实测 0.378，会红——**这是对的**）；`dusk_br` 同理
- [ ] **2.4 常量侧**：让 `DAY_GND_HORIZON` / `DUSK_GND_HORIZON`
  向对应的 `*_SKY_HORIZON` 靠；试 `sky_curve` 调到接近地平线时已收敛
- [ ] **2.5 重拍 `12b_day` + `12c_dusk` 同机位 A/B**

## 第三批：黄昏草皮饱和度 + 把判据换到像素上（半天）

**已确认的事实**

| | 中位 sRGB | 中位饱和度 |
| :--- | :--- | :-: |
| 正午草带 | (159,166,86) / (94,133,73) | 0.474 / 0.450 |
| **黄昏草带** | **(81,55,15)** / (25,32,17) | **0.796** / 0.514 |

**草皮自身 albedo 的蓝通道**决定（`blade_base` b=0.270 / `ground_color` b=0.285），
太阳色降纯度几乎不动那个乘积。

  **另外补两条量像素的**：
  - 「黄昏草带中位饱和度 `≤ 0.55`」（实测 0.796）
  - 正对照「正午草带中位饱和度 `≤ 0.50`」（实测 0.474）
- [ ] **3.2 调旋钮**，二选一：
  - 抬 `grass.gdshader` 的 `blade_base` / `blade_tip` / `ground_color` / `ground_dark`

## 第六批：那 27 秒（**先做实验，不许直接改**）

**已确认的事实**：去第 5 站，站心在路外 10m，
满油门 15.0 m/s 持续约 27 秒，距目标在 18~27m 之间振荡。
**与第四轮的读数一字不差**（第四轮：30 秒从 27m 只走到 18m）。

**分不清**：这是**产品问题**（草皮 + 软边界真的推着车）
还是**路径问题**（自动机在追一个路点而画了个圈）。
量了一轮仍然分不清。**所以这一批的第一件事不是改代码。**

- [ ] **6.1 写一个把两者分开的探针**（新脚本，不进产品）：
  站在「站心与最近路点连线的中点」，朝站心直线冲 10 秒，
  每帧记录：到站心距离、到中心线距离、`_apply_boundary_force` 的推力大小、
  实际速度。**推力显著大于 0 而速度上不去 = 产品问题；推力≈0 = 路径问题**
- [ ] **6.2 按 6.1 的结论分岔**
  - 若是产品问题 → 在 `SOFT_BOUND` 外再画一道引导（`RoadVerge` 已经有形状，
    缺的是「往哪骑」的指向），**不要削弱推力**：
    削弱推力会让人真的骑进 25m 的硬墙里
  - 若是路径问题 → 改 `play_newcomer.gd` 的路点选取，
    **并且在它成为回归门槛之前，先把 `STATION_OFFSET = 18.0` 与
    `STATION_PASS_RADIUS = 15.0` 这两个数的语义在注释里说清楚**
    （玩家在 3m 外就够得着打卡圈，并不需要真的骑到 18m）
- [ ] **6.3 定阈值**：现在只有一个读数，**不足以定门槛**。
  6.1 的探针跑出 p95 之后，才把「最后 20m 平均速度 ≥ X m/s」写进回归

## 不在本计划里的（以及为什么）

  第五批 5.4 是「诚实」的解法（没有去处就不显示）；
  造经济系统是另一个量级的工作，不该由一轮评审顺手塞进来。

  文件头已经写明为什么不能改（`alpha_to_coverage` 在 Compatibility / Web 上
  不实现）。这是一个**正当的取舍**。要改的是它的**代价没有被量化**，
  而不是那个取舍本身。放进 P2 观察，不进排期。
- **路碑 / 交叉点那块碑的辨识度**——
  第五批 5.5 已经把「要么有判据、要么明确接受它不出现」摆出来了。
  在那之前，任何关于它好不好看的意见都没有判据支撑。
